# REA and Ghidra: reading notes

Read 2026-10-12 from clones at `/home/claude/read/rea` (morluto/rea, 2,596 commits, 1,281 TypeScript source files, 253,715 lines, 94 registered MCP tools) and `/home/claude/read/ghidra` (NSA Ghidra, 15,826 Java files). Four fresh Opus readers each read a slice of the source in full and reported with file:line; the claims below that carry the most weight were re-checked against the files by hand. Nothing was run; neither repo's dependencies were installed.

## What REA is

A local MCP server and CLI that lets a coding agent reverse engineer a target: native binaries through Hopper, Ghidra or IDA, JavaScript and Electron apps, .NET, Android, firmware, websites, process behaviour. It does not analyse anything itself in the deep sense; it owns the process that does, and it turns every answer into an Evidence record the agent can cite.

Three ideas carry the whole project.

**1. Evidence is content-addressed and authenticated on every read.** `src/domain/evidence.ts:110-129` is the strict record: subject (digest, format, architecture), provider, analysis_profile, predicate_type, operation, parameters, raw_result, normalized_result, confidence (`observed | derived | inferred`), authority (`shipped-artifact | controlled-replay | historical-reference | external-service | analyst-inference`), environment, limitations, locations, evidence_links. Its id is `ev_` plus SHA-256 of a canonical projection that excludes the display name and path (`evidence.ts:234-263`, comment: "Hash semantic content, including raw results and excluding display-subject fields"). Parsing recomputes the id and rejects a mismatch (`evidence.ts:158-168`). Records are deep-frozen and registered in a module-private WeakSet so a plain `Object.freeze` cannot forge one (`immutableJson.ts:48`).

**2. Unknowns are first-class records with a hash chain.** `residualUnknown.ts:81-121`: question, status (`open | investigating | blocked | contradicted | resolved`), severity, supporting and contradicting evidence ids, required authority and confidence, probes, relationships, resolution, and mutation evidence. Revisions chain by digest; updates are compare-and-swap on `expected_revision`. A `verified` resolution needs at least one supporting evidence record that meets the required authority exactly and the confidence rank; mutation evidence cannot count, and "Withdrawn and out-of-scope dispositions are not truth claims" (`sessionToolContracts.ts:157`).

**3. Nothing claims more than it can prove.** Replays say so ("Loaded from a local REA analysis snapshot; this call did not re-run the provider", `AnalysisSnapshotCache.ts:310`). An oversized result is never truncated; the full record is kept and a reference returned (`toolResult.ts:189`). Static relationships "must remain inferred" and every inferred fact needs a limitation (`javascriptApplicationEvidenceSchemas.ts:293, 360-375`). An empty obligation ledger is `unknown`, not `ready`: "No reconstruction obligations were derived; closure cannot be claimed" (`ReconstructionObligationLedgerEvaluation.ts:162`). Provider selection has no silent priority: "Registration order never affects selection or caller-visible output" (`AnalysisProviderRegistry.ts:72`), and two usable candidates is an error, not a pick.

Other load-bearing mechanics:

- Tool annotations are derived only from a declared effects record, never from names (`toolEffects.ts:617-640`, verified). Every tool needs an effects audit entry or registration throws. Unknown tools are treated as returning untrusted target content so a new path never loses the marker.
- The Ghidra bridge is a `HeadlessScript` run as the last post-script of `analyzeHeadless -readOnly -deleteProject`, serving newline-delimited JSON over a 0600 Unix socket with a 32-byte token compared in constant time; the handshake must echo run id, profile digest and target sha256 exactly (`GhidraSessionValues.ts:72-110`). The target is copied into a private root and hashed before Ghidra ever sees it. Annotations commit only after readback matches, else roll back (`ReaGhidraBridge.java:1102-1152`).
- Process supervision: children in their own process group with a run token in their environment; before any kill every member's token is re-read, bracketed by start-time checks so PID reuse is caught (`ProcessOwnership.ts:231-277, 672-733`). "REA never kills a process it cannot prove it owns" (`docs/mcp-contracts.md:383`, verified). Failed cleanup is retained and retried, never reported as success.
- The analysis profile (provider plus parameters plus digest) is part of Evidence identity, so results under different analysis settings never share an id or a cache entry.
- Testing doctrine: real public CLI/MCP workflows first, then production-boundary integration, then goldens from real producers; "simulated providers do not establish real-provider behavior" (`AGENTS.md`). New capabilities are fail-closed: "Passing CI, completed implementation, upstream popularity, or silence from maintainers is not scope approval" (`CONTRIBUTING.md:75-80`).

Defects the readers found: a derived workflow that runs twice in one session with different evidence hits `already-exists` on the shared unknown and drops its Evidence (`EvidenceLedger.ts:283-289`); `verify_unknown_resolution` promises revalidation but only reads the head's status (`EvidenceLedger.ts:366-382`); docs say a fresh connection has its own ledger, but the ledger is process-wide (`main/transport.ts:91-93`). Not run, so not confirmed.

## What Ghidra is

A reverse engineering framework: disassembly, decompilation, scripting, a debugger, and a team workflow. Two halves matter here.

**The analysis core.** A `Program` is memory, a symbol table, an equate table and a listing (`Program.java:47-59`), with managers for functions, references, data types, bookmarks, and a transaction requirement on every write (`DomainObject.java:45-47`). Every symbol, signature and reference carries a `SourceType` with a priority: `DEFAULT 1 < ANALYSIS 2 = AI 2 < IMPORTED 3 < USER_DEFINED 4` (`SourceType.java:44-66`, verified; `AI` is its own value at storage id 4). Writers check the priority before overwriting, so an analyzer, or an AI, cannot clobber what a person wrote. Instructions are decoded by SLEIGH processor specs into p-code, a processor-neutral register transfer language (COPY, LOAD, STORE, BRANCH, CALL, INT_*, FLOAT_*, plus analysis-only MULTIEQUAL, INDIRECT, CAST, PTRADD and others, `PcodeOp.java:46-138`), which is why one decompiler serves every processor. The decompiler is a separate native process that pulls bytes, p-code, symbols and types from Java by callback and "automatically respawns" if it crashes (`DecompInterface.java:41-47`); its output is a `HighFunction` that is not written to the database unless a caller commits it with a source type (`HighFunctionDBUtil.java:242`). Analysis is event-driven over address sets, in a fixed priority order where "earlier analyzers are generally more sure" and late ones "tend to be more speculative" (`AnalysisPriority.java:32-42`). Headless mode runs pre-scripts, analysis, post-scripts; `-readOnly` discards, `-deleteProject` removes a project it created, and script-requested deletion is refused without `-okToDelete` (`HeadlessAnalyzer.java:1210-1214`, verified).

**The team half: Ghidra has its own version control.** A project file is a property file plus a `~name.db` directory of 16 KB buffer files. Versions are stored as the latest full file plus reverse deltas per older version (`LocalManagedBufferFile.java:206-233, 640-645`). Checkouts are NORMAL, EXCLUSIVE or TRANSIENT, the last lasting only while the client connection is alive (`CheckoutType.java:25-43`). Structural edits (the memory map) require an exclusive checkout, enforced at the edit (`DomainObjectAdapter.java:352-353`). Check-in needs a clean state: "File has unsaved changes", "File recovery data exists" (`GhidraFileData.java:1654-1659`). The server re-verifies the checkout owner on every write (`RepositoryFile.java:205-207`). If someone else checked in first, a merge runs over four inputs, ORIGINAL, LATEST, MY, RESULT, per facet and per field: what only one side touched is applied automatically, a conflict exists only where both touched the same thing and differ (`MergeUtilities.java:40-43`), and choices include KEEP_BOTH and "use for all". When your checkout is revoked your work is not lost; it becomes a visible "hijacked" copy or a `name.keep` file (`GhidraFileData.java:1148, 1984`). The index is rewritten atomically with a backup and a journal, and can be rebuilt from the property files alone.

Its weaknesses, which are the exact things git is for: nothing works offline (checkout, check-in, update all need the server); one in-memory server per repositories directory with no replication; no content hashing or signatures; and the merge always opens a modal GUI, even with zero conflicts, so headless check-in refuses: "Checkin failed, file requires merge which is not supported in headless mode" (`GhidraFileData.java:1693`, verified; `MergeManager.java:150-177`, verified). Also a doc bug: the storage doc puts file 00001234 under folder "12" but the code uses the 3rd and 2nd hex digits from the right, "23" (`IndexedLocalFileSystem.java:252-255`, verified).

## What this means for Sim Locker

Git is good at the thing Ghidra is bad at (offline, distributed, content-addressed, no central memory) and bad at the thing Ghidra is good at (structured records, field-level merge, locks tied to the edits that cannot merge, source-of-truth tags, revoked work kept as a visible copy). REA shows how to make a store that AI agents can be trusted with: every write is a content-addressed, authenticated record with a declared confidence and authority; unknowns are records too; effects are declared and permissions derived from them; nothing silently truncates, falls back or claims closure; processes and locks are proven before they are destroyed.

So Sim Locker is git for storage and transport, with a record layer above it that borrows these:

1. Four states, named once: saved (local, with crash snapshots), backed up (on GitHub), accepted (merged to the truth branch after a review record), live (deployed). Ghidra's transaction, save and check-in map onto the first three; version tracking's "accepted without applied" maps accepted against live.
2. A `source` on every record: human, imported, analysis, AI, default, with Ghidra's rule that lower cannot overwrite higher without a human.
3. Records are content-addressed and re-hashed on read (REA). Display fields stay out of the hash.
4. Change sets, not text diffs, drive merges (Ghidra's `ProgramDBChangeSet`); conflict only where both sides touched the same field and differ; the no-conflict case completes without a human, which is the one thing Ghidra refuses to do.
5. Leases that die with the agent (TRANSIENT checkout) for the few edits that cannot merge; everything else unlocked.
6. Revoked or superseded work becomes a named, visible side copy, never a loss (`.keep`, hijack).
7. Declared effects per operation, permissions derived from them, destructive operations need a second key (`-okToDelete`), and the store never deletes or force-pushes what it cannot prove the actor owns.
8. Unknowns and reviews are records with their own ids and chains, and "done" needs qualifying evidence; withdrawing is not truth.
9. Everything an agent produces is a scratch, read-only run until a named actor promotes it (`-readOnly -deleteProject`, uncommitted HighFunction).
10. The page a person reads is generated from the records, like REA's `inspect_analysis_view`, and never hand-edited.
